# Telegram-бот реабилитационного центра (MVP v1)

Принимает заявки клиентов по 9 сценариям, складывает их в SQLite и дублирует в
Google Таблицу. Long polling, `aiogram 3.x`, `SQLAlchemy 2.0` (async), Alembic.

> **CRM-панель** для этих же данных — в папке [`crm/`](crm/) (Next.js + Supabase,
> деплой на Vercel). Общая с ботом база Postgres. См. [`crm/README.md`](crm/README.md).

## Возможности

| # | Сценарий | Тип |
|---|----------|-----|
| 1 | Запись в общий зал | дата → время → аппарат → ФИО → телефон, пишет прямо в реальную таблицу расписания клиники |
| 2 | Запись к инструктору | дата → время → ФИО → телефон, лимит записей на слот |
| 3 | Запись на домашнюю программу | первичный / повторный выезд |
| 4 | Расписать домашнюю программу | линейная форма |
| 5 | Реакции обострения | срочное уведомление админам, без формы |
| 6 | Покупка расходных материалов | линейная форма |
| 7 | Техосмотр оборудования | линейная форма |
| 8 | Вопросы по договору | линейная форма |
| 9 | Другое | линейная форма |

Сценарии 3, 4, 6, 7, 8, 9 описаны декларативно в `bot/scenarios.py` и
обрабатываются одним универсальным движком (`bot/handlers/generic_form.py`).

## Требования

- Python 3.11+
- Токен бота от [@BotFather](https://t.me/BotFather)
- (опционально) Google service account для записи в таблицу

## Быстрый старт (локально)

```bash
python3.11 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

cp .env.example .env
# заполните BOT_TOKEN и ADMIN_CHAT_IDS

alembic upgrade head        # создать схему БД (bot/main.py тоже делает это при старте)
python -m bot.main
```

Отправьте боту `/start`.

## Создание бота у @BotFather

1. Напишите [@BotFather](https://t.me/BotFather) → `/newbot`.
2. Задайте имя и username (должен заканчиваться на `bot`).
3. Скопируйте выданный токен в `BOT_TOKEN` в `.env`.
4. Узнайте свой числовой chat_id (например, через [@userinfobot](https://t.me/userinfobot))
   и впишите его в `ADMIN_CHAT_IDS` (несколько — через запятую).

## Google Sheets

Бот работает с **двумя независимыми Google-таблицами**:

1. **Лог заявок** (`GOOGLE_SHEET_ID`) — плоский список для сценариев 2-9: лист
   «Заявки», по строке на обращение. Опционален: если ID пуст — бот работает,
   просто не дублирует заявки в таблицу.
2. **Таблица расписания зала** (`GYM_SCHEDULE_SHEET_ID`) — реальная таблица
   администратора с листом на каждый день (`31.08 ПН`, `01.09 ВТ`, …) и сеткой
   «слот × аппарат». Это сценарий 1: бот пишет ФИО прямо в свободную ячейку и
   читает её же перед записью — **таблица является источником истины по
   занятости**, а не БД (если администратор вписал клиента вручную — бот это
   увидит). Без этого ID запись в зал отвечает «временно недоступна», но
   остальной бот работает.

### Настройка service account (общая для обеих таблиц)

1. [console.cloud.google.com](https://console.cloud.google.com/) → создайте проект.
2. **APIs & Services → Library** → включите **Google Sheets API**.
3. **APIs & Services → Credentials → Create credentials → Service account**.
4. У созданного аккаунта: **Keys → Add key → JSON**. Скачанный файл сохраните как
   `credentials.json` в корне проекта (путь настраивается в `GOOGLE_CREDENTIALS_PATH`).
5. **Лог заявок:** создайте новую таблицу, ID из URL
   (`https://docs.google.com/spreadsheets/d/<ID>/edit`) → `GOOGLE_SHEET_ID`.
   При старте бот сам создаст лист «Заявки» с нужными заголовками.
6. **Таблица расписания:** возьмите ID существующей таблицы клиники →
   `GYM_SCHEDULE_SHEET_ID`. В ней должны быть листы-шаблоны для дублирования
   на новый день — их имена настраиваются через `GYM_TEMPLATE_WEEKDAY` /
   `GYM_TEMPLATE_SATURDAY` (по умолчанию «копия пн-пт» / «копия сб»).
7. В **обеих** таблицах: **Share** → доступ **Editor** на email service account
   (вида `...@....iam.gserviceaccount.com` из `credentials.json`).

Если Google API недоступен, заявка (сценарии 2-9) всё равно принимается, а
строка досылается фоновой задачей (`bot/services/sync.py`, retry с backoff).
Для сценария 1 такого «отложенного» пути нет — занятость аппарата нельзя
подтвердить без живого чтения таблицы, поэтому при недоступности Sheets бот
явно сообщает об этом, а не принимает запись вслепую.

## Запуск в Docker

```bash
cp .env.example .env            # заполнить BOT_TOKEN, ADMIN_CHAT_IDS
touch credentials.json          # или положить реальный ключ service account
docker compose up --build
```

БД сохраняется в `./data/bot.db` на хосте.

## Переменные окружения

| Переменная | По умолчанию | Описание |
|------------|--------------|----------|
| `BOT_TOKEN` | — | токен бота (обязательно) |
| `ADMIN_CHAT_IDS` | — | chat_id админов через запятую |
| `EMERGENCY_PHONE` | — | телефон дежурного администратора (сценарий 5) |
| `DATABASE_URL` | `sqlite+aiosqlite:///./data/bot.db` | строка подключения |
| `GOOGLE_SHEET_ID` | пусто | ID таблицы лога заявок (сценарии 2-9); пусто = отключено |
| `GOOGLE_CREDENTIALS_PATH` | `./credentials.json` | путь к ключу service account (общий для обеих таблиц) |
| `GYM_SCHEDULE_SHEET_ID` | пусто | ID таблицы расписания зала; пусто = сценарий 1 недоступен |
| `GYM_TEMPLATE_WEEKDAY` | `копия пн-пт` | имя листа-шаблона для будних дней |
| `GYM_TEMPLATE_SATURDAY` | `копия сб` | имя листа-шаблона для субботы |
| `GYM_APPARATUS_COUNT` | `8` | аппаратов в общем зале |
| `TIMEZONE` | `Asia/Almaty` | часовой пояс расписания |
| `BOOKING_HORIZON_DAYS` | `14` | на сколько дней вперёд открыта запись |
| `WORKING_DAYS` | `1,2,3,4,5,6` | рабочие дни (1=Пн … 7=Вс) |
| `INSTRUCTOR_SLOTS_PER_HOUR` | `2` | макс. записей к инструктору на один сеанс |
| `LOG_LEVEL` | `INFO` | уровень логирования |
| `SHEET_SYNC_INTERVAL_SECONDS` | `30` | период фоновой синхронизации |
| `SHEET_SYNC_MAX_ATTEMPTS` | `20` | максимум попыток отправки строки |

## Архитектурные заметки

- **Сценарии 2-9: БД — источник правды, Google Sheets — витрина.** Заявки живут
  в SQLite; в лог-таблицу данные дублируются асинхронно и отказоустойчиво
  (`sheet_sync_queue` + фоновый ретрай с backoff).
- **Сценарий 1: наоборот — источник истины сама таблица расписания.** Бот
  читает ячейку `[слот × аппарат]` перед записью: пусто → пишет, что-то есть →
  «занято» (в том числе если это вписал администратор вручную). Запись под
  `asyncio.Lock` на дату + повторная проверка ячейки прямо перед записью
  исключают гонку двух одновременных подтверждений на один аппарат. БД
  (`gym_bookings`) — необязательное зеркало для истории и уведомлений; её сбой
  не откатывает уже сделанную запись в таблице.
- **Движок форм на конфигах:** новый линейный сценарий (3-9) добавляется правкой
  `bot/scenarios.py` — без новых хендлеров.
- **Слой `repo.py`** не знает про aiogram; хендлеры не пишут SQL напрямую.
