## Роль и задача

Ты — senior Python-разработчик. Нужно с нуля написать production-ready Telegram-бота для реабилитационного центра. Бот принимает заявки от клиентов по 9 сценариям и складывает их в базу данных и Google Таблицу.

Перед началом покажи план файлов проекта и дождись подтверждения. Затем реализуй по частям, проверяя, что код запускается и импортируется без ошибок.

## Стек (обязательный)

- Python 3.11+
- **aiogram 3.x** (async, FSM через `StatesGroup`, storage — MemoryStorage на v1)
- **SQLite + SQLAlchemy 2.0** (async, драйвер `aiosqlite`), миграции через Alembic
- **gspread** (или `google-api-python-client`) с service account для Google Sheets
- `pydantic-settings` для конфигурации из `.env`
- Long polling (не webhook)
- Логирование через стандартный `logging`, уровень из `.env`
- Dockerfile + docker-compose.yml

## Ключевые архитектурные требования

### 1. Движок форм на конфигах

Сценарии 2, 3, 4, 6, 7, 8, 9 — это линейные формы одного типа. **Не пиши для каждого отдельный хендлер.** Опиши их декларативно в `scenarios.py` (или YAML) и сделай один универсальный обработчик, который прогоняет любой конфиг.

Формат шага:

```python
{
    "key": "consumables",
    "title": "Покупка расходных материалов",
    "steps": [
        {"id": "item", "type": "choice", "question": "Что нужно приобрести?",
         "options": ["Гель", "Кабель", "Другое"]},
        {"id": "item_other", "type": "text", "question": "Уточните, что именно нужно",
         "show_if": {"item": "Другое"}},
        {"id": "full_name", "type": "text", "question": "Укажите ваше ФИО"},
        {"id": "phone", "type": "contact", "question": "Оставьте номер телефона"}
    ]
}
```

Поддерживаемые `type`: `choice` (inline-кнопки), `text` (свободный ввод), `contact` (кнопка «Поделиться номером» через `request_contact` + возможность ввести вручную), `date` (выбор даты из календаря).

Условная логика — через `show_if` (шаг показывается, только если предыдущий ответ совпал).

### 2. База данных — источник правды, Google Sheets — витрина

Google Таблица нужна клиенту для просмотра, но **не должна быть хранилищем состояния**. Все брони и заявки живут в SQLite. В Sheets данные дублируются.

Запись в Sheets — асинхронная и отказоустойчивая: если Google API недоступен, заявка всё равно принята, а строка попадает в таблицу `sheet_sync_queue` и отправляется повторно фоновой задачей (retry с backoff). Пользователь никогда не видит ошибку Google API.

### 3. Защита от двойной брони

На таблице бронирований зала — `UNIQUE(session_date, session_time, seat_number)`. Создание брони — в транзакции, с обработкой `IntegrityError`: если место успели занять, показать пользователю «Место уже занято, выберите другое» и вернуть к выбору мест.

## Модель данных

```
users
  id, telegram_id (unique), username, first_name, phone, created_at

requests                      # заявки по линейным сценариям
  id, user_id, scenario_key, payload (JSON), full_name, phone,
  status (new/processed), created_at

gym_bookings                  # записи в общий зал
  id, user_id, session_date, session_time, seat_number,
  full_name, phone, status (active/cancelled), created_at
  UNIQUE(session_date, session_time, seat_number)

instructor_bookings           # записи к инструктору
  id, user_id, session_date, session_time, full_name, phone, created_at

sheet_sync_queue
  id, sheet_name, row_data (JSON), attempts, last_error, synced_at
```

## Сценарии

### Главное меню (`/start`)

Inline-кнопки:

1. Запись в общий зал
2. Запись к инструктору
3. Запись на домашнюю программу
4. Расписать домашнюю программу
5. Реакции обострения
6. Покупка расходных материалов
7. Техосмотр оборудования
8. Вопросы по договору
9. Другое

---

### 1. Запись в общий зал (единственный нелинейный сценарий)

Флоу: **дата → время → место → ФИО → телефон → подтверждение**

- Календарь inline-кнопками. Показывать только даты в пределах горизонта записи (`BOOKING_HORIZON_DAYS`, по умолчанию 14) и только рабочие дни. Прошедшие даты недоступны.
- После выбора даты — список слотов из `WORKING_HOURS` с указанием загрузки: `10:00 — свободно 3 из 6`. Полностью занятые слоты помечены 🚫 и некликабельны.
- После выбора слота — сетка мест: `Место 1 ✅ / Место 2 🚫`. Занятые не кликаются.
- Все параметры (рабочие дни, часы работы, длительность слота, количество мест) — в конфиге, не хардкодить.
- Один пользователь не может занять два места в одном слоте.

### 2. Запись к инструктору

Дата → время → ФИО → телефон. Слоты те же, но без выбора места; ограничение по количеству записей на слот — из конфига (`INSTRUCTOR_SLOTS_PER_HOUR`).

### 3. Запись на домашнюю программу

Выбор: **а) Первичный выезд** / **б) Повторное обращение**

- Первичный: ФИО → желаемая дата → телефон.
- Повторное: «Укажите причину повторного выезда» (текст) → ФИО → желаемая дата → телефон.

### 4. Расписать домашнюю программу

ФИО → телефон → комментарий (необязательно).

### 5. Реакции обострения — ОСОБЫЙ СЦЕНАРИЙ

Это не форма. Это медицинская срочность.

- Пользователю сразу показать контакт дежурного администратора (телефон из `.env`) и кнопку «Позвонить».
- Предложить коротко описать состояние (текст, необязательно).
- **Немедленно** отправить уведомление всем `ADMIN_CHAT_IDS` с пометкой `🔴 СРОЧНО — РЕАКЦИЯ ОБОСТРЕНИЯ`, именем, username, телефоном и текстом.
- Не заставлять проходить многошаговую форму.

### 6. Покупка расходных материалов

Выбор: Гель / Кабель / Другое (с уточнением текстом) → ФИО → телефон.

### 7. Техосмотр оборудования

ФИО → телефон → комментарий (необязательно).

### 8. Вопросы по договору

Выбор: Расторжение договора / Докупить количество занятий / Другое (с уточнением) → ФИО → телефон.

### 9. Другое

Текст обращения → ФИО → телефон.

## Требования к UX

- Всё на inline-кнопках, минимум ручного ввода.
- Кнопка **«⬅️ Назад»** на каждом шаге + **«❌ Отмена»** — возврат в главное меню.
- `/start` в любой момент сбрасывает состояние FSM.
- Перед отправкой — **экран подтверждения** со сводкой всех ответов и кнопками «✅ Подтвердить» / «✏️ Изменить».
- После отправки — сообщение с номером заявки: `Заявка №142 принята. Мы свяжемся с вами.` + кнопка «В главное меню».
- Телефон: кнопка `request_contact` + возможность ввести вручную, с валидацией формата (казахстанские номера: `+7XXXXXXXXXX`, нормализовать к единому виду).
- ФИО: минимум 2 слова, только буквы/дефис/пробел, длина 3–100.
- Все тексты сообщений — в одном модуле `texts.py` (русский), чтобы клиент мог править без залезания в логику.
- Часовой пояс — `Asia/Almaty`, вынести в конфиг.

## Google Sheets

Service account, ID таблицы в `.env`. Два листа:

**Лист «Заявки»** — колонки:
`Дата создания | Тип обращения | Telegram ID | Username | ФИО | Телефон | Детали | Статус`

**Лист «Записи в зал»** — колонки:
`Дата создания | Дата занятия | Время | Место | ФИО | Телефон | Telegram ID | Статус`

При старте бот проверяет наличие листов и заголовков, создаёт их, если нет.

## Уведомления администраторам

`ADMIN_CHAT_IDS` (список через запятую в `.env`). На каждую новую заявку — сообщение админам с типом, ФИО, телефоном, деталями и ссылкой на пользователя (`tg://user?id=...`). Сценарий 5 — отдельным ярким форматом, отправляется первым делом, до записи в БД.

## Критерии готовности

1. `docker compose up` поднимает бота, он отвечает на `/start`.
2. Все 9 сценариев проходятся до конца и создают запись в БД.
3. Данные появляются в обеих вкладках Google Таблицы.
4. Если отключить интернет до Google — заявка всё равно принимается, а после восстановления строка досылается.
5. Две параллельные попытки занять одно место — вторая получает корректное сообщение, а не 500.
6. `README.md` содержит: установку, создание бота у @BotFather, создание service account и выдачу доступа к таблице, запуск локально и в Docker.

Пиши чистый типизированный код с докстрингами. Не используй устаревший синтаксис aiogram 2.x.
